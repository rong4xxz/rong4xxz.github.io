# Skill 的卸载

首先介绍一下当前流行的 Agent 的 skill 的卸载机制

# Claude Code

对于 claude code 来说，不是采用卸载，而是自动压缩时按 token 预算淘汰，规则如下：

| 规则 | 说明 |
| --- | --- |
| 每个已调用 skill 保留前 5000 tokens | 压缩时，保留该 skill 内容的前 5000 tokens |
| 所有 skill 共享 25000 tokens 预算 | 所有已被调用过的 Skill 合计占用不超过 25000 tokens |
| 按最近调用顺序填充预算 | 较新的 Skill 优先保留，较早的超出预算则被**丢弃** |


## 举例说明

举例来说，可以想象一个餐厅后厨，有一个操作台，最多放 25000 tokens。初始的时候，桌子上只有一个清单，
罗列了你会做的菜（占据的 token 非常少。等到客户下单“酸菜鱼”后，你需要找到“酸菜鱼”的菜谱（SKILL.md
，占据了 7000 token ），放在操作台上，然后随着新的订单来，你还需要找到“小炒肉”的菜谱（占据 12000
token）。这下操作台上只剩下 6000 token 的空间了，但是又来了新的“鸡蛋羹”订单（需要占据 10000 
token），这个时候开始从加载的第一份菜谱开始压缩，把“酸菜鱼”菜谱折起来，只漏出来第一页（5000 token）
，这样又有位置放“鸡蛋羹”菜谱了。但是随着订单越来越多，最后会出现所有的已经放在操作台上的菜谱都折起来
了（5000 token），这个时候还需要放新的菜谱的话，就直接从最长时间没用的菜谱开始撤掉（如果后面又做了
一次酸菜鱼，就撤掉小炒肉，给新的菜谱腾位置。

# 其他 Agent

目前除了 Claude Code 以外，其他的 Agent 都没有显示的针对 skill 的卸载机制，基本上都是将 
skill 视为普通上下文，等到压缩上下文的时候一起作为历史记忆被压缩

# 思考

目前来说基本上大家对于 skill 的生命周期管理不是很重视，然而在真实的应用场景中，对于 skill 的生命
周期管理是必要的，这不仅能降低 token 成本，同时也能够降低噪声，在某些场景下提升 LLM 的表现。

当然，对于子 agent / worker 来说，基本上是不需要做 skill 管理的，因为基本上子 agent 的生命
周期就是 skill 的生命周期。
