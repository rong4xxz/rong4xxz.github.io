## 一、上下文工程简介

### 1.1 是什么

**一句话**：一套让LLM在有限上下文窗口里看到最该看到的信息的策略。

**三个概念的区分**：

- **记忆**：存什么（硬盘里的文件）
- **上下文工程**：怎么管存取（文件系统 + 内存管理）
- **提示词工程**：这次怎么排版（指令集优化）

### 1.2 为什么需要它

人类交流是高熵的（混乱、有潜台词），LLM只理解低熵的明确指令。

Agent时代的四个具体痛点：
1. **混淆**：冗余信息淹没关键指令
2. **冲突**：多轮信息自相矛盾
3. **干扰**：关键信息被次要内容淹没
4. **Lost in Middle**：模型注意力集中在头尾（注：新模型已基本解决这个问题）

### 1.3 怎么做：四大策略

| 策略 | 要解决的问题 | 典型做法 |
| :--- | :--- | :--- |
| **写入** | 存什么、怎么存 | 短期记忆（滑动窗口）+ 长期记忆（向量库） |
| **选择** | 用的时候取哪些 | 三维召回：相关性+时效性+重要性 |
| **压缩** | 信息太多怎么办 | 语义摘要、结构化转换、RL智能压缩（如Meta REFRAG） |
| **隔离** | 防止互相污染 | 任务专属缓冲区、安全沙箱 |

### 和Agent记忆的关系

```text
记忆体系（有什么信息）→ 上下文工程（怎么塞进去）→ 上下文窗口（LLM看到的世界）
```

**一句话**：记忆是“存了什么”，上下文工程是“怎么管存取”，提示词工程是“这次怎么排版”。

### 面试金句

> “把LLM比作操作系统，上下文窗口就是RAM，上下文工程就是内存管理单元（MMU）。”

## 二、如何实现上下文工程

### 2.1 写入策略

写入策略关心的是存什么和怎么存，一般分为短期记忆和长期记忆

#### 2.1.1 短期记忆

短期记忆是一个分层管理的三块内容

| 层级       | 名称                             | 存什么                                   | 格式                  | 生命周期                  |
| :--------- | :------------------------------- | :--------------------------------------- | :-------------------- | :------------------------ |
| **第一层** | 当前工作记忆（Working Memory）   | 当前任务的中间状态：进度、待办、中间结果 | 结构化JSON            | 当前任务结束即清空        |
| **第二层** | 对话历史（Conversation History） | 用户和助手的多轮对话原文                 | JSONL（每行一条消息） | 滑动窗口，超出则丢弃/压缩 |
| **第三层** | 会话元数据（Session Metadata）   | 会话级别的附属信息                       | JSON                  |                           |

##### a. 当前工作记忆

- 存什么：当前任务执行过程中的”草稿纸“状态

- 怎么存：使用 json 格式，典型的数据结构如 Hermes 的三元组设计[^1]，存储在内存中，读写快

- 生命周期：会话结束即销毁（可以从对话历史中恢复）

- 示例：**（未采用三元组设计）**

  ```json
  {
    "current_task": "用户投诉处理-订单ORDER-12345",
    "progress": "已完成订单核实，正在查询配送记录",
    "intermediate_results": {
      "order_status": "已签收",
      "delivery_time": "2026-05-15 14:30"
    },
    "remaining_steps": ["生成补偿方案", "发送回复"],
    "constraints": {
      "remaining_budget": 20,
      "max_reply_tokens": 500
    }
  }
  ```

[^1]: 三元组设计是工作记忆的核心数据模型，本质是把工作记忆拆成主主体、谓词和对象。因为三元组是知识图谱中最基本的知识表达形式，有三个好处：结构化、可组合以及可追溯

##### b. 对话历史

- 存什么：用户和 Agent 的完整对话记录
- 怎么存：使用 jsonl 文件存储一个 session，每行 json 代表一条消息，每条消息至少包含 `role/content/timestamp/turn_id/metadata(可选)`
- 生命周期：长期保存

- 示例：

  ```json
  # sessions/2026-05-16/session_ji8fs435g5d5h.jsonl
  {"role": "user", "content": "波士顿天气怎么样？", "timestamp": 1700000000, "turn_id": 1}
  {"role": "assistant", "content": null, "tool_calls": [{"id": "call_1", "name": "get_weather", "arguments": {"location": "Boston"}}], "timestamp": 1700000001, "turn_id": 1}
  {"role": "tool", "tool_call_id": "call_1", "content": "{\"temp\": 22, \"condition\": \"sunny\"}", "timestamp": 1700000002, "turn_id": 1}
  {"role": "assistant", "content": "波士顿今天22度，晴天", "timestamp": 1700000003, "turn_id": 1}
  ```

##### c. 会话元数据

- 存什么：这次对话本身的信息，不是对话内容，用来判断是否需要压缩/清理，或者会话恢复，或者按用户/设备维度做个性化

- 怎么存：一般采用 json 格式

- 生命周期：长期保存

- 示例：

  ```json
  {
    "session_id": "abc123",
    "user_id": "user_456",
    "device": "mobile",
    "subscription_tier": "premium",
    "active_tasks": ["投诉处理-ORDER-12345"],
    "turn_count": 42,
    "estimated_tokens_used": 8750,
    "created_at": 1700000000,
    "last_activity": 1700000500
  }
  ```

#### 2.1.2 长期记忆
