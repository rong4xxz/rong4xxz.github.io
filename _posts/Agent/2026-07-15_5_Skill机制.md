# Skill机制

对于 Skill 机制来说，一开始 Claude Code 官方给的定义就是可复用的流程文档，说的绕口一点叫做“**基于提示词的对话上下文和执行上下文修改器**”。目的是为了让 Agent 在面对一些重复性很高的任务时，能够直接根据之前的经验，以最优路线和方案去解决，所以本质上，其实还是提示词工程。

# What？

Skill 看起来就像一本针对任务 A 的说明书，你可以让 Agent 自己决定什么时候要去读这份说明书，当然，也可以指定 Agent 先去读这本说明书。它长下面这样：

```markdown
---
name: 操作电视机
description: 教学如何操作电视机
allowed-tools: 安装APP，打开APP
---
这个技能的目的是为了教学你如何操作电视机
# 步骤
## 1. 安装豆包
首先打开应用市场，搜索豆包，点击下载并安装
## 2. 打开豆包
安装完毕后，打开豆包，点击右上角的电话图标，并打开摄像头
## 3. 询问豆包
豆包可以看到你的摄像头拍摄到的内容，你有什么疑问都可以问豆包😁
```

> 当然上面的 Skill 只是主包搞怪的

# How？

那么技能如何使用呢？由于 Anthropic 公司最早推出 Skill 机制并制定标准，导致后来大家都只能遵守这个标准，所以我们就来看看 Skill 的标准到底是啥把：

```plain
skill-name/
├── SKILL.md          # 必需：元数据 + 指令
├── scripts/          # 可选：可执行脚本
├── references/       # 可选：参考文档
├── assets/           # 可选：模板、资源
└── ...               # 其他任意文件
```

+ SKILL.md：这个文件就是上面的说明书
+ scripts/：这个目录的作用是提供一些自动化脚本帮助 LLM 更好的使用这个 skill，比如说提供一个自动化脚本叫做“安装APP”，LLM 看见这个说明书直接调用这个脚本，传递一个参数“-app 豆包”即可完成步骤1。
+ references/：这个目录的作用是提供一些参考文档
+ assets/：提供一些模板和资源

## 安装 Skill

那对于 AI Agent 来说，需要统一管理这些 Skill，根据上面的标准就很容易想到了，所有的 Skill 都是一个文件夹，那我用一个专门的文件夹来存储 LLM 能用的 Skill 不就行了？这个时候就出现了 skills/ 目录。同时还要区分有些技能是只在 A 项目中会用到，比如 部署 A 项目的运行环境；有些技能是全局通用的，比如说 操作电视机😁。所以一般对于 AI Agent 来说，会有两个 skill 文件夹：

+ `~/.ai-agent/skills/<skill-name>/`← 个人级（所有项目可用）
+ `./.ai-agent/skills/<skill-name>/`← 项目级（仅当前项目，位于当前项目根目录下）
+ `<plugin>/skills/<skill-name>/`← 插件级（这个我觉得需要单独拉出来讲，见 [参数化技能](./2026-07-16_参数化技能.md)）

一般来说，对于 AI Agent 来说，有一键安装的功能，目的是为了方便后台管理 skill，具体来说就是把 skill 的文件夹放进你指定的 skills/ 目录

然后 AI Agent 每次启动的时候，扫描这些目录，如果有 SKILL.md，并且格式正确（有YAML格式的元数据可以读取），那就读取这些**元数据**，放到 LLM 上下文中，这样就等于 LLM 可以看到自己可以调用哪些技能，分别可以用来做什么了，这就等于安装并注册成功了！

## 加载 Skill

### 懒加载

有些人可能注意到上面的安装中，我特意提到 AI Agent 在读取的时候读取的是元数据。也就是安装电视机 Skill 中的这部分：

```yaml
---
name: 操作电视机
description: 教学如何操作电视机
allowed-tools: 安装APP，打开APP
---
```

这是因为 SKILL.md 一般来说都特别长，如果全都塞进 LLM 上下文中，会导致成本很高，同时会产生很多和当前任务无关的噪声，所以 Anthropic 就想了“懒加载”的方法，所有的 skill 一开始在 LLM 上下文中大约只有一个技能名称和描述，大概长下面这个样子：

```plain
Skill A: name="操作电视机", description="教学操作电视机..."
Skill B: name="测试", description="写测试用例..."
```

当 LLM 在推理中认为现在需要使用某个技能了，就会触发技能的加载，这会把**技能的 SKILL.md **读取放进大模型上下文中。

### 三层渐进式披露

上面懒加载提到的是技能的 SKILL.md 会被读取，那还有 scripts/、references/这些目录的资料呢？由于这些资料 LLM 不一定需要读取，另外一次性把这些都读进去会导致上下文过大，所以这部分就让 LLM 觉得需要读取的时候，自己读就好。所以把 LLM 可能需要读取的资料的引用放在 SKILL.md 中，这样 Agent 如果需要读取，则会自己调用读取文件的工具读取这些资料。大概像下面这样：

```plain
---
name: 操作电视机
description: 教学如何操作电视机
---
# 步骤
1. xxx
2. xxx
3. xxx
## 参考文档
- [电视机说明书](./references/instruction.md)
- [零件清单](./references/list.md)
```

电视机说明书和零件清单只在 Agent 觉得需要的时候才会去读取

### 手动加载
但是 skill 始终存在一个问题，就是 agent 不一定会调用，因为它觉得目前不需要使用这个技能。所以一般 agent 还会提供一个功能：**手动加载**

大家在使用各种 AI IDE 的时候，大部分都有 "/" 启动某个命令/技能的功能，基本上为了用户方便，在你输入 "/" 的时候就会出现一堆候选，你能在其中看到你安装的技能，这和 agent 加载技能是一样的，本质上是强制往 agent 运行上下文中塞入对应技能的 SKILL.md

## 卸载 Skill

大部分时候大家关注的都是什么时候加载 skill，但是很少有人去探讨什么时候卸载 skill。结合我们之前的描述，加载了 skill 以后，SKILL.md 的内容就会一直在上下文中，然后现有的 AI Agent 普遍策略为，这个 SKILL.md 会一直在上下文中直到会话结束。

然而现实情况是很多时候我们在一个会话中，做的不仅仅是和当前 skill 相关的事，一个 skill 可能只是其中的一个子步骤，这个子步骤完成后，已经不需要这个 skill 了，这个时候如果继续在这个会话中聊下去，会造成大量的 token 浪费，以及对后续任务的噪声。所以我们在加载 skill 后，什么时候卸载 skill 也是很重要的。

由于这部分比较重要，所以我用了单独的笔记来介绍，见 [skill的卸载](./2026-07-23_SKILL的卸载.md)
