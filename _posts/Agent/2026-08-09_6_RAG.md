# RAG (Retrieval Augmented Generation) 检索增强生成

在 RAG 技术出现之前，LLM 回答问题时，通过自身在训练时学到的知识，生成最终的答案。这存在几个问题：

第一个就是 LLM 的幻觉问题，由于 LLM 在训练以后，知识都变成了权重参数，在回答问题的时候又是根据概率去回答你的问题（详见 [模型架构](../LLM/2025-07-04_模型架构.md)），所以就算没有相关知识或者 LLM 没有答案，也并不会坦诚的说不知道，而是开始编造答案。

第二个则是时效性，大多数 LLM 的知识都截止在训练数据收集的那一刻，之后发生的事情，它完全无法知道。如果想让 LLM 知道的话，基本上需要继续收集数据，进行新一轮的训练。

第三个是定制大模型的问题，LLM 基本上训练集中都是公共知识，对于一些业务性比较强的场景，LLM 没有任何知识背景，完全无法使用，除非收集相关数据，进行 LLM 微调（详见 [LLM微调](埋个坑)），这样成本依旧很高。

于是 Facebook AI Research 团队在 2020 年提出了 RAG 技术（论文《Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks》，发表于 NeurIPS 2020），这项技术本质上是为 LLM 提供一个外部的非参数化知识库（可以检索的文档），来增强生成内容的准确性和事实性。这样能一并解决上面的 3 个问题！

说起来很抽象，什么叫做一个非参数化知识库？首先想象一下知识库中应该是一条条的知识（普通文本），如果只是简单的把这些知识收集起来，那么很快就会面临两个问题，怎么存起来？存起来怎么用？也就是怎么检索需要的知识？

接下来，我们按**"从地基到塔尖"**的层级，系统性地梳理 RAG 的进化版图。

---

# 第一层：知识存储形态（知识长什么样，存在哪里）

这一层只关心**知识是怎么存储和表达的**，不关心怎么检索。

## 1. 纯文本模式（古法RAG）

### 知识的存储

最古老，最朴素，最容易想到的方式自然就是所有的知识同等级别，是一串字符串，整个知识库就是这些字符串的合集（列表或集合）。

### 知识的召回

在这种情况下，主要采用关键词匹配。例如，问题是"一斤苹果一般情况下多少钱？"。这个时候就在海量的知识库中查找"苹果"和"价格"这两个词的文件。

- 优点：精准，一定只会搜到预期内的知识
- 缺点：死板，可能还会搜到"苹果手机"相关的知识，也搜不到"Apple"相关的知识，因为关键词不匹配

## 2. 向量模式

### 知识的存储

这种方法是为了解决纯文本的"死板"问题而诞生的，把文字转成向量。我们来看看一条知识是怎么被转换为向量的，以目前非常主流的开源模型 `bge-large-zh` 为例：

**第一步：分词（Tokenizer）**

我们拿到知识文本后，不是直接交给模型的，而是先把汉字拆成一个个的 token id：

- 输入："一斤苹果大概2块钱"
- 输出：`[101, 2341, ..., 5362]`（一串由数字组成的列表，长度假设为 L）

**第二步：Embedding 查表（嵌入层）**

然后把这些 token id 转换为初始的向量矩阵：

- 机制：模型内部有一张巨大的 "Embedding 词表"，每个 id 都有一条固定的向量（比如 512 维）
- 操作：把刚刚那串数字 id，挨个去词表里查，把 id 替换为向量
- 结果：得到了一个 `L * 512` 的初始矩阵。此时的向量只代表"词"，不理解上下文（比如"苹果"和"华为"在此时向量很接近）

**第三步：Encoder 编码（深层 Transformer 层）**

这一步把"词向量矩阵"变成"富含上下文语义的矩阵"：

- 机制：把初始矩阵送入 12 层或 24 层的 Transformer 编码器。每一层都会让矩阵里的每一个向量去"看"矩阵里所有其他的向量（自注意力机制），从而让每个 token 吸收整个句子的上下文信息
- 结果：经过多层计算后，`L * 512` 的矩阵里，每个 token 的向量都已经吸收了它前后文的全部信息。此时，"苹果"这个词的向量已经知道它是"水果"而不是"公司"了（因为上下文里有"一斤"）

**第四步：池化（Pooling）**

这一步把 `L * 512` 的矩阵压缩成 `1 * 512` 的单一向量：

- CLS 池化：只取矩阵的第一行（[CLS]标记对应的向量）作为整句话的代表，BERT 系常用
- 平均池化：把矩阵里所有 L 个向量按列求平均，得到一个平均向量，`bge` 系列、`text-embedding-ada-002` 等主流模型都用这种

**第五步：L2 归一化**

为了让后面算余弦相似度更快，大多数向量模型在输出的最后做一次归一化，把那条 `1 * 512` 的向量除以自身的长度（模长），使得它的模长变成 1：

- 最终结果：一条模长为 1、维度为 512（或 768/1024/1536）的浮点数向量，这就是最终存进向量数据库的那条"知识向量"

值得注意的是：**一条知识在存储时 = 一条向量**。虽然中间过程会经过一个矩阵的形态，但最终会被"压扁"成一条向量。之所以要这么做，是因为向量数据库（如 Milvus、Qdrant）索引的基本单位就是一条向量，而且变成向量后可以用数学上的"距离计算"（如余弦相似度）来快速找到相似的知识，配合 ANN（近似最近邻）[^1] 索引（如 HNSW 算法[^2]），能在百万级数据中实现毫秒级检索。

[^1]: ANN 是一种索引策略，核心是在庞大的备选向量中，不追求绝对精确，而是在极短的时间内找到足够像的前几十个；

[^2]: HNSW 是 ANN 的一种实现算法，思路是在向量入库的时候，生成一张“多跳地图”，类似于世界地图，给你一个地点，查找位置的时候，先根据所处洲，然后确定国家，最后是省份、城市、县城，最后只需要在县城范围内搜索最相近的就行了。

### 知识的召回

用户的问题同样会走一遍完整的"分词 → Embedding → Encoder（含注意力）→ 池化 → 归一化"流程，变成一条向量后，再通过 ANN 索引在向量库中找到最相似的 Top-K 条知识。注意，注意力计算只发生在"文本变成向量"这一步，后面的向量比对只是纯粹的数学距离运算，不再涉及 Transformer。

- 优点：能理解语义，用户搜"苹果多少钱"也能匹配到"一斤苹果大概2块钱"相关的知识，不再局限于字面匹配
- 缺点：不够精确，可能把"苹果17手机大约5000元"也搜出来，因为向量只看"意思相近"而不看"类别是否一致"

## 3. 知识图谱模式（GraphRAG）

### 知识的存储

知识图谱不只看单个知识，而是**显式地存储实体之间的关系**，形成一个"实体-关系"网。它的基本组成单位是**三元组（SPO）**：

- 主语（Subject）、谓语（Predicate）、宾语（Object）
- 例如："苹果属于水果" → `(苹果) -[属于]-> (水果)`

这些三元组不会存成普通表格，而是存放在专门的图数据库（如 Neo4j）里，因为图数据库天生就适合存储和查询这种"点"和"边"的结构。

### 知识图谱的构建

构建过程分为两步：

**第一步：从文本中抽取事实（实体 + 关系）**

以句子"深度求索（DeepSeek）公司于 2023 年 7 月 17 日在杭州成立，由梁文锋创办"为例：

1. 实体抽取：识别出"深度求索公司"（机构）、"杭州"（地点）、"梁文锋"（人物）、"2023年7月17日"（时间）
2. 关系抽取：识别出"深度求索公司 → 成立于 → 2023年7月17日"、"深度求索公司 → 总部位于 → 杭州"、"深度求索公司 → 由...创办 → 梁文锋"

在工业界，这一步通常采用**"廉价 NLP 工具做粗加工，大模型做精装修"**的分层策略：

- **廉价 NLP 工具（如 spaCy、HanLP）**：基于规则 + 统计，跑在 CPU 上，毫秒级完成，成本几乎为零。它先通过词典匹配识别实体，再通过依赖句法分析找出主谓宾结构，最后用正则模板（如 `{实体A} 创办 {实体B}`）抽取关系，详见 [NLP工具](埋个坑)
- **大模型救场**：当廉价工具的置信度低于阈值（如 0.7）、或抽出了实体但没抽出关系、或与外部知识库比对发现遗漏时，系统才会触发大模型（如 GPT-4）来处理，并用严格约束的 Prompt 强制输出 JSON 格式的三元组
- **模板自举进化**：大模型产出的新关系模式，经过频率考验、质检和冲突测试后，会被自动翻译成正则表达式，反哺到廉价 NLP 的模板库中，形成一个"越用越便宜"的正反馈循环

**第二步：存入图数据库**

抽取出的三元组被存入图数据库（如 Neo4j），供后续检索使用。

## 4. 多模态模式

多模态 RAG 让系统能处理**图片、表格、扫描件、音频、视频**等多种形式的数据。核心挑战在于不同模态的向量不在同一个"语义空间"，因此工程上通常先做**语义对齐**：用 OCR 从图片中提取文字，或用模型为图片生成一段文字描述（Caption），再将这些转化为可检索的文本，从而巧妙地融合进现有流程。

## 5. 小结：第一层四种存储形态的对比

| 存储形态 | 知识表达方式 | 存储介质 | 擅长解决的问题 |
| :--- | :--- | :--- | :--- |
| 纯文本 | 原始字符串 | 列表/集合/ES | 精确关键词匹配 |
| 向量 | 浮点数向量 | 向量数据库（Milvus/Qdrant） | 语义相似搜索 |
| 知识图谱 | 实体-关系-实体三元组 | 图数据库（Neo4j） | 多跳逻辑推理 |
| 多模态 | 图片/表格转文本描述 | 上述任意一种 | 非文本数据的理解 |

这四种形态是**平级**的，它们解决不同的问题，可以共存于同一个系统中。

# 第二层：检索策略（怎么查，用什么工具查）

这一层建立在第一层的存储之上，决定当用户提问时，系统**调用哪些存储**来获取知识。

## 1. 单路检索

只用一种存储来检索：

- 仅向量检索：只查向量库，适合语义类问题
- 仅关键词检索（BM25）：只查关键词索引，适合精确匹配类问题
- 仅图检索：只查知识图谱，适合关系推理类问题

## 2. 混合检索（Hybrid Search）

**同时**使用"向量检索 + 关键词检索（BM25）"，把两路结果合并、去重、按相关性排序：

| 文本ID | 原始纯文本内容 | 向量数值 | 关键词标签 |
| :--- | :--- | :--- | :--- |
| 001 | "特斯拉Cybertruck交付量突破10万辆" | [0.12, -0.56, ...] | 特斯拉, Cybertruck, 交付 |
| 002 | "某国产电动皮卡发布，对标特斯拉" | [0.33, -0.21, ...] | 电动皮卡, 国产, 对标 |

混合检索结合了两种方式的优点：

- 向量检索负责语义理解，找出意思相近的内容
- 关键词检索（BM25）负责精确匹配，确保不遗漏专有名词（如 `useEffect`、合同编号 `HT-2026-001`）

BM25 本质上是一个数学计算公式（排序算法），它不只看词在不在，还会计算词频（出现次数越多得分越高）、逆文档频率（生僻词得分高）和文档长度（短文更可能聚焦主题），因此比单纯的关键词匹配更智能。

## 3. 图检索

走知识图谱，进行多跳遍历（子图扩展）：

- 从用户问题中抽取出实体（如"梁文锋"）
- 在图里进行多跳遍历：`梁文锋 → 创办 → 深度求索 → 发布 → DeepSeek-V2`
- 把整条路径上的节点和关系全部捞出来作为证据链

图检索适合回答"A和B什么关系？""A公司的CEO是谁？"这类需要多步推理的问题。

## 4. 多路融合

同时走"混合检索"和"图检索"，把两路结果合并、去重、排序后，统一交给 LLM 生成答案：

- 混合检索提供"语义相关的文本块"
- 图检索提供"精确的关系路径和实体链"
- 两者互补，既保证了语义召回率，又保证了推理的精确性

## 5. 小结：第二层检索策略的对比

| 检索策略 | 调用的存储 | 适用场景 |
| :--- | :--- | :--- |
| 单路检索 | 一种存储 | 简单场景，单一需求 |
| 混合检索 | 向量 + 关键词索引 | 需要同时兼顾"语义理解"和"精确匹配" |
| 图检索 | 知识图谱 | 需要多跳关系推理 |
| 多路融合 | 上述多种组合 | 复杂问题，需要全方位覆盖 |

**"混合检索"和"图检索"是同一层级的两种检索策略**，它们可以组合使用（多路融合）。

# 第三层：控制模式（谁来控制查询流程）

这一层是 RAG 的**"大脑"**所在，它决定**检索过程由谁控制、何时停止、是否迭代**。

## 1. 普通 RAG（固定流程）

**代码写死**的流程：用户问一个问题，系统查一次（无论用的是单路还是混合检索），把 Top-K 条结果直接喂给 LLM 生成答案，然后结束。整个过程是固定的，LLM 没有机会说"这些资料不够，我再查点别的"。

```python
def normal_rag(user_question):
    # 1. 这步是写死的：不管问什么，都只查一次
    retrieved_docs = search(user_question, top_k=5)
    
    # 2. 这步也是写死的：查完立刻生成，不再回头
    final_answer = llm.generate(question=user_question, context=retrieved_docs)
    
    return final_answer
# 缺点：如果查到的5篇文档里没有答案，它就废了，绝对不会再试一次。
```

## 2. 高级 RAG / Agentic RAG（LLM 主导的迭代流程）

核心变化是：**把"查询"这件事交给 LLM 自己控制**。LLM 不再是等着被喂数据的"工具人"，而是变成了整个检索流程的"主控器"。

用伪代码表示就是：

```python
def agentic_rag(user_question):
    notebook = []  # 记录所有已查到的信息
    max_rounds = 5
    
    for i in range(max_rounds):
        # 1. LLM 自己决定怎么查（拆解问题、换个关键词、换块知识库）
        search_queries = llm.think_and_decide(question=user_question, previous_notes=notebook)
        
        # 2. 执行查询（可以调用第二层的任意检索策略：混合检索、图检索等）
        new_docs = execute_search(search_queries)
        
        # 3. LLM 自己 Review 查到的资料
        review_result = llm.review(notes=notebook, new_docs=new_docs)
        
        # 4. 核心决策：LLM 根据 Review 结果判定是否足够
        if review_result == "信息已足够，可以作答":
            break
        else:
            notebook.append(new_docs)  # 记下来，进入下一轮
    
    # 循环结束后，拿着累积的全部证据生成最终答案
    final_answer = llm.generate(question=user_question, context=notebook)
    return final_answer
```

**普通 RAG = 代码写死的单次检索**；**高级 RAG（Agentic RAG）= LLM 自己控制循环，自己决定何时停止**。

### Agentic RAG 的约束机制

这种"把决策权交给 LLM"的模式如果不加约束，LLM 可能会陷入死循环或收集一堆噪声。因此工程上会给它戴上三重"手铐"：

1. **工具白名单**：开发者预先定义好一套严格的工具集（如 `search_vector_db`、`search_bm25`、`search_knowledge_graph`），LLM 只能使用这些工具，不能乱跑
2. **系统提示词约束**：在 System Prompt 里写入硬性规则，如"最多执行 3 次检索循环"、"查不到就承认，严禁编造"
3. **裁判员评分器**：引入一个专门负责"挑刺"的小模型或规则引擎，对检索到的每篇文档进行相关性评分，低于阈值（如 0.7）的文档直接丢弃，不让 LLM 看到这些噪声

### 检索迭代的终止条件（"三重门"）

Agentic RAG 在进行多轮检索时，不会无限循环下去，而是通过"三重门"来决定何时停止：

| 门禁 | 判断逻辑 | 触发停止条件 |
| :--- | :--- | :--- |
| **硬性限制** | 当前迭代轮数 >= 5 | 立即停止，保底防死循环 |
| **信息增益门** | 本轮新增信息量 < 15%（与历史所有内容相比） | 软性停止，认为信息已饱和 |
| **答案置信度门** | 草稿答案自信评分 > 85 分 | 提前终止，认为足以作答 |

### Agentic RAG 可以调用第二层的任意检索策略

**高级 RAG（Agentic）可以调用混合检索，也可以调用图检索，甚至同时调用两者**。它是凌驾于具体检索方法之上的"总指挥"。

```
│  └── 高级 RAG / Agentic RAG：LLM 主导，带循环和反思              │
│          │                                                        │
│          │ （可以任意调用下面的检索策略）                         │
└──────────┼────────────────────────────────────────────────────────┘
           │
┌──────────┼────────────────────────────────────────────────────────┐
│ 第二层：检索策略（怎么查，用什么工具查）                         │
│  ├── 单路检索（仅向量 / 仅关键词 / 仅图谱）                     │
│  ├── 混合检索（向量 + 关键词 BM25，两路合并）                   │
│  ├── 图检索（多跳遍历，子图扩展）                               │

│  ├── 向量模式（Embedding + ANN 索引）                           │
│  ├── 知识图谱模式（实体-关系-实体，存图库）                    │
│  └── 多模态模式（图片/表格转文本描述后存储）                    │
└─────────────────────────────────────────────────────────────────────┘
```

# Q&A

## 1. RAG 解决了幻觉问题吗？

**没有完全解决，但大幅降低了。**

RAG 把幻觉的"来源"从"模型记忆"转移到了"检索到的文档"上。它解决了"因为记不清而编造"的幻觉（闭卷变开卷），但引入了新的问题：

| 类型 | 描述 | 示例 |
| :--- | :--- | :--- |
| 检索失败 | 向量库里没有正确答案，或没搜出来 | 用户问"A公司财报"，库里只有"B公司财报"，LLM 会编造一份 |
| 上下文过载 | 检索回来的文档太长，LLM 漏看了关键信息 | 返回了 50 页 PDF，LLM 漏掉了最后一页的"不含税"三个字 |
| 矛盾处理 | 多篇文档互相矛盾，LLM 随机选了一个 | 一篇说"致死率 2%"，另一篇说"0.5%"，LLM 取了个平均值 |
| 忠实于错误 | LLM 把原文里的错误或谣言也照搬出来 | 检索到一篇谣言帖，LLM 直接当作事实回答 |

因此，RAG 是一个强大的**"降噪器"**（把幻觉率从 50% 降到 10%），但不是一个**"过滤器"**。想从 10% 降到 1%，需要引入 Agent 的自我反思、多轮验证和引用溯源机制——让 LLM 不仅要回答，还要为自己的每句话配上证据，配不上证据的话宁可不说。

## 2. RAG 和 Memory 是什么关系？

首先 RAG 中存储的是确定性的知识，无论换什么 LLM，换什么用户，都可以正常使用。而 Memory 存储的是 Agent 历史轨迹，包括用户的喜好、任务进度等。换一个用户就无法使用了。但是两者都涉及到存储和召回，且两者之间是可以配合使用的。
用户询问问题，首先查询 RAG，获取相关知识，然后查询 Memory，获取用户偏好和历史轨迹，最后给出结果。
