众所周知，大部分人是没有条件在本地部署自己的大模型的，就导致大部分时候我们的 AI 应用还是通过调用第三方厂商的服务。那么问题就来了，既然是调用服务，那就需要制定协议，也就是我们常说的 API。

一般来说，常见的 LLM API 模式就三种，分别是 Chat Completions、Responses、Messages，前两个是 OpenAI 提出的标准，后者则是 Anthropic 公司提出的标准。另外还有不常见的两种，App Server 帧以及 Converse API。

# API 详解

## Chat Completions

该 API 的核心协议是向 `/v1/chat/completions` 端点发送一个 POST 请求，请求体则为一个 JSON 对象，包含一些参数来控制模型的输入和输出行为。

### 请求体格式

```json
{
  "model": "deepseek-v4-flash",
  "messages": [
    {"role": "system", "content": "你是一名个人智能助理。"},
    {"role": "user", "content": "明天出门要不要带伞？"}
  ],
  "temperature": 0.2,
  "top_p": 0.9,
  "response_format": {
    "type": "json_object"
  },
  "stream": false,
  "tool_choice": "auto",
  "tools": [
    {
      "type": "function",
      "function": {
        "name": "get_weather",
        "description": "获取指定城市的当前天气信息。当用户询问天气时使用。",
        "parameters": {
          "type": "object",
          "properties": {
            "location": {
              "type": "string",
              "description": "城市名称，例如：北京、上海"
            },
          },
          "required": ["location"]
        }
      }
    }
  ]
}
```

参数解释：
- 必选
  - model: 指定你想调用的 LLM 名称，如果错误，则调用该模型就会失败
  - messages: 对话的上下文，这个数组非常重要，是 Agent 中上下文工程的基础。可以看到在消息列表开头有一个系统消息，主要作用是设定模型的人格、行为准则或全局指令，一般用来放和具体问题无关的提示词。紧接着是用户提示词，一般用来记录具体的用户问题。在 LLM 上下文中，系统提示词的权重会比用户提示词更大，也就是说对 LLM 的影响会更大，这主要是由于模型在训练和微调阶段学会的。
- 可选
  - temperature: 控制文本生成的随机性，0 - 2，值越低，输出越确定和聚焦，值越高，输出越多样化和有创造性。实际上这个原理是通过对计算出的输出 token 的原始概率分布进行缩放，然后从被调整过的分布中采样。[^1]
  - top_p: 核采样的概率阈值，也是控制随机性的另外一种方法，0 - 1，如果 top_p = 0.9，意味着只会采样概率达到 90% 的 token，从而忽略掉一些概率比较低的 token。
  - response_format: 输出格式，用于强制模型按照指定的格式输出，大部分时候用 `{"types": "json_object"}`，用来确保模型输出的内容是一个合法的 json，方便程序解析，更进一步的 json_schema 模式可以约束输出必须符合你定义的 JSON Schema。[^2]
  - stream: 设为 true 的时候，API 会通过 SSE 逐字或逐词地流式返回生成的内容，能给用户提供更快的”首字响应”体验。
  - tool_choice: 设为 "auto" 让模型自己决定是否调用工具，或者 "required" 要求必须调用工具，或者 "none" 要求不准调用工具，或者给一个 object 如 `{"type": "function", "function": {"name": "X"}` 要求使用指定的工具。
  - tools: 给模型的一份工具清单，模型可以通过输出 tool_call 来调用这清单中的工具，具体格式如上面示例，需要包含工具名称、参数等。其中的 required 字段表示必填参数


[^1]: 这个过程严格遵循一个数学公式：$调整后的logits = 原始logits / temperature$，这里的 logits 就是指的模型输出的、**未经过归一化**的原始分数。`softmax` 函数会将 logits 进行归一化，而 `temperature` 通过调整 logits 的缩放比例，直接改变了 `softmax` 函数的最终输出，也就是每个 token 的概率分布的“平坦“或”尖锐“程度。越尖锐，采样的时候就会总是最高的那个，越平坦，采样的时候就可能挑中不同的词，因为大家差距都不大。
[^2]: response_format的原理分为两个层级。
基础层级就是 `{"type": "json_object"}`，首先 API 后端会在 messages 列表最前面插入一条系统指令，告诉 LLM 要输出一个合法的 JSON 对象，以 `{` 开头，以 `}` 结尾。然后在模型逐字生成 Token 的过程中，解码器会**实时校验**生成的 Token 是否符合 JSON 语法，比如模型生成了一个 `{`，解码器会限制下一个 Token 不能是非法字符，比如 `]`。但是这种模式只能保证合法 JSON，不能保证包含预期字段。
高级层级就是 `{"type": "json_schema"}`，API 会将传入的 JSON Schema 定义转化为一个上下文无关语法 CFG，定义了所有符合要求的”语法规则“，在模型生成每个 Token 前，解码器会参考这个 CFG，**动态计算**出下一个 Token 的合法候选集，任何不符合的 Token 会被直接屏蔽，模型只能从合法的候选集中进行采样。

### 响应体格式

```json
{
  "id": "chatcmpl-dw3ffw4ff...",
  "object": "chat.completion",
  "created": 172412334,
  "model": "deepseek-v4-flash",
  "system_fingerprint": "fp_abc123def456",
  "choices": [
    {
      "index": 0,
      "message": {
        "role": "assistant",
        "content": null,
        "tool_calls": [
          {
            "id": "call_abc123",
            "type": "function",
            "function": {
              "name": "get_weather",
              "arguments": "{\"location\": \"上海\"}"
            }
          }
        ]
      },
      "finish_reason": "tool_calls",
    }
  ],
  "usage": {
    {
      "prompt_token": 25,
      "completion_token": 42,
      "total_tokens": 67,
      "prompt_toeken_details": {
        "cache_tokens": 0
      },
      "completion_token_details": {
        "reasoning_tokens": 0
      }
    }
  }
}
```

字段解析：
- id: 本次调用的唯一标识符，用作日志追踪、错误排查、账单核对用的
- object: 对象类型，固定为 `"chat.completion"`，用户客户端区分响应类型
- created: 响应生成的时间
- model: 实际使用的模型名称，可能会与请求的 `model` 不同
- system_fingerprint: 系统指纹，表示模型后端的版本或配置快照，当模型行为发生变化时，可以通过追踪这个值的变化来追踪问题
- choices: 这是最重要的部分，包含了模型生成的回复。这是一个数组，因为你可以通过 `n` 参数请求**多个候选回复**[^3]，通常 n = 1。每个数组中一般含有下面字段：
  - index: 候选回复的序号，从 0 开始编号
  - message: 模型生成的消息对象，包含 `role`（固定为 assistant） 和 `content`
  - delta: 流式模式下的增量内容，message 被替换为 delta，每次只返回新增的文本片段
  - finish_reason: 生成结束的原因，这是判断响应类型的关键标志。通常有 5 种取值：`stop`（模型自然结束）、`length`（生成达到 max_tokens 导致被截断）、`tool_calls`（模型需要调用工具）、`content_filter`（内容被安全过滤器拦截）、`null`（流式传输还没完成时）
  - logprobs: 对数概率信息，如果在输入中请求了 `logprob` 参数，则会包含每个 Token 的详细概率数据。
- usage: 这个对象用于计费和性能监控：
  - prompt_token: 输入消耗的 token 数
  - completion_tokens: 输出消耗的 token 数
  - total_tokens: 总和
  - prompt_token_details.cached_tokens: 缓存命中的 token 数
  - completion_token_details.reasoning_tokens: 内部思考的 token 数
  
### 流式响应格式

```json
data: {"id":"chatcmpl-abc123","object":"chat.completion.chunk","created":1725334567,"model":"gpt-4o-2024-08-06","system_fingerprint":"fp_xyz789","choices":[{"index":0,"delta":{"role":"assistant"},"finish_reason":null}]}

data: {"id":"chatcmpl-abc123","object":"chat.completion.chunk","created":1725334567,"model":"gpt-4o-2024-08-06","system_fingerprint":"fp_xyz789","choices":[{"index":0,"delta":{"content":"Chat"},"finish_reason":null}]}

data: {"id":"chatcmpl-abc123","object":"chat.completion.chunk","created":1725334567,"model":"gpt-4o-2024-08-06","system_fingerprint":"fp_xyz789","choices":[{"index":0,"delta":{"content":" Completions"},"finish_reason":null}]}

data: {"id":"chatcmpl-abc123","object":"chat.completion.chunk","created":1725334567,"model":"gpt-4o-2024-08-06","system_fingerprint":"fp_xyz789","choices":[{"index":0,"delta":{"content":" API"},"finish_reason":null}]}

data: {"id":"chatcmpl-abc123","object":"chat.completion.chunk","created":1725334567,"model":"gpt-4o-2024-08-06","system_fingerprint":"fp_xyz789","choices":[{"index":0,"delta":{},"finish_reason":"stop"}]}

data: [DONE]
```

在流式响应中，响应是一系列的 SSE 格式的数据块，每个块都是一个 json 对象，逐步拼凑出完整回复。如上方示例：
- 第一块是角色声明，声明回复的角色是 `assistant`，此时 content 还是空的
- 第二块到第n-1块是内容增量，每个数据块携带一小段文本片段，客户端需要将这些 `content` 字符串按顺序拼接起来，形成完整回复。
- 最后一块是结束标志，此时包含 `finish_reason`，且 `delta` 为空对象。紧接着 `data:[DONE]` 表示传输彻底结束。


## Responses API

Responses API 是 OpenAI 在 Chat Completion API 基础上推出的新一代 API，主要目的是为了简化和统一。和 Chat Completion API 最大的区别是引入了有状态的概念。当前这里要注意，LLM 本身还是无记忆的，只不过是服务器通过 `previous_response_id` 这个参数来记住之前的对话。

该 API 的核心协议是向 `/v1` 端点发送一个 POST 请求

### 请求体格式

```json
{
  "model": "deepseek-v4-flash",
  "input": "明天上海出门要带伞吗？",
  "instructions": "你是一名个人智能助理。",
  "max_output_tokens": 300,
  "temperature": 0.7,
  "reasoning": {"erroft": "high"},
  "text": {"type": "json_object"},
  "tool_choice": "auto",
  "tools": [
    {
      "type": "function",
      "function": {
        "name": "get_weather",
        "description": "获取某个城市的天气预报",
        "parameters": {
          "type": "object",
          "properties": {
            "location": {
              "type": "string",
              "description": "想要获取天气预报的城市名"
            }
          },
          "required": ["location"]
        }
      }
    }
  ]
}
```

可以看到 `messages` 数组已经被 `input` 和 `instruction` 替代了。此外还有一些新的字段：
- reasoning: 对于支持推理能力的模型，控制其思考深度
- text: 类似于 Chat Completion API 的 response_format 字段
